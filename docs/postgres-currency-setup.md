# PostgreSQL currency setup (PayMongo simulation)

This backend stores Diamonds and permanent purchase receipts in PostgreSQL. Classic Coins stay in PlayFab `CO`; Unity game Gold is not moved. The website continues to validate the signed test-mode PayMongo payment before fulfillment. A success-page visit never credits a wallet.

Provisioning the database and installing the schema are operator actions, not something `npm run dev`, deployment, or the verifier performs automatically. No live-payment enablement is included.

## 1. Keep purchases disabled

Keep both gates off during setup:

```dotenv
PLAYFAB_DIAMONDS_ENABLED=false
COIN_CHECKOUT_ENABLED=false
PLAYFAB_COINS_RECEIPTS_VERIFIED=false
```

These gates do not stop an older deployed revision that does not read them. Use your existing rollout controls if an older version is still accepting payments. Do not manually set database verification flags to `true` just to remove an unavailable message.

Before changing a previously used backend, read the migration section below. An empty database is not evidence that an old paid order was never granted.

## 2. Create a PostgreSQL database

On Vercel, open the project connected to **your fork**, not an upstream project. Use a PostgreSQL integration from [Vercel Marketplace](https://vercel.com/docs/marketplace-storage), such as [Neon](https://vercel.com/marketplace/neon/neon), and connect the resource to that project. Review the provider's current terms, region, backup options, and usage limits before provisioning; this document does not promise a free plan or unlimited storage.

You may use another compatible PostgreSQL provider instead. Use isolated test/preview databases where appropriate. Never point an unreviewed preview branch at the production purchase ledger merely because the provider automatically supplies a connection string.

## 3. Install the schema with an administrator credential

Open `database/currency-schema.sql` and read its deployment instructions. Execute it deliberately through your provider's SQL editor or a trusted PostgreSQL administrator tool. Configure the correct PlayFab title (`17FA03` for this test title) and retain the installation UUID generated by the schema.

The migration creates the `civilcraft_currency` schema and the `civilcraft_currency_app` **NOLOGIN** permission group. As the administrator, create a separate login with a privately chosen strong password, then grant only that group:

```sql
CREATE ROLE civilcraft_currency_runtime LOGIN PASSWORD '<privately chosen strong password>';
GRANT civilcraft_currency_app TO civilcraft_currency_runtime;
ALTER ROLE civilcraft_currency_runtime SET statement_timeout = '15s';
SELECT database_id, title_id, schema_version FROM civilcraft_currency.installation;
```

Run this SQL only in your private administrator tool, not as a website request. The installation query returns the UUID used for `CURRENCY_DATABASE_ID`. Confirm `title_id` is `17FA03`; a different title requires a deliberately configured installation, not relabeling an existing paid ledger.

For Neon, create this restricted login with SQL, **not** the Console's **Add role** button, CLI, or API. Those other creation paths automatically grant `neon_superuser` membership, including administrative privileges; such a role must not become the website runtime credential. SQL-created roles receive limited privileges and need the explicit group grant above. [Neon role privileges](https://neon.com/docs/manage/roles)

Use a direct administrator connection for migration/role setup. For the website's serverless requests, choose the restricted login's pooled connection string if your provider supports it. The `ALTER ROLE` timeout applies on new PostgreSQL connections; reconnect/redeploy after changing it. The driver deliberately does not send `statement_timeout` as a startup parameter or rely on a persistent session `SET`, which can fail with transaction pooling. The read-only verifier checks schema and credential restrictions, not timeout configuration or every provider pool setting; verify the real chosen endpoint before enabling purchases. [Neon pooling limitations](https://neon.com/docs/connect/connection-pooling), [PgBouncer startup parameters](https://www.pgbouncer.org/config#ignore_startup_parameters)

The migration owner is an administrative role. The website must connect as that separate restricted runtime login, with only the schema/function permissions described by the migration. It must not own the schema/tables, inherit the owner role, create objects in the currency schema, or directly insert/update/delete/truncate wallet and receipt tables. Do not use the provider's default owner connection string as `CURRENCY_DATABASE_URL`.

The schema health function checks the installation/title/schema binding and the connected runtime role's privileges. If your provider's role setup does not pass those checks, keep checkout disabled and correct the privileges; do not weaken the checks.

## 4. Configure private local values

Use a private, git-ignored `.env` file in the website root. Keep all keys and connection strings out of chat, screenshots, commits, and browser code. Node's `--env-file` loads the values without printing their contents. Do not create `VITE_CURRENCY_DATABASE_URL` or any other public-prefixed copy of a secret.

```dotenv
VITE_PLAYFAB_TITLE_ID=17FA03
PLAYFAB_SECRET_KEY=<existing private title secret>
PAYMONGO_SECRET_KEY=<existing sk_test_ key>
PAYMONGO_WEBHOOK_SECRET=<existing test endpoint signing secret>
PUBLIC_APP_URL=https://civil-craft-website.vercel.app

PLAYFAB_DIAMONDS_STORAGE=postgres
COIN_RECEIPTS_STORAGE=postgres
CURRENCY_DATABASE_URL=<restricted runtime connection string with provider TLS settings>
CURRENCY_DATABASE_ID=<installation UUID from the schema>
CURRENCY_DATABASE_VERIFIED=false
CURRENCY_DATABASE_VERIFIED_TITLE_ID=
CURRENCY_DATABASE_VERIFIED_CONFIG_SHA256=
PLAYFAB_DIAMONDS_ENABLED=false
COIN_CHECKOUT_ENABLED=false
PLAYFAB_COINS_RECEIPTS_VERIFIED=false
```

Retain PlayFab `CO` configuration and all unrelated website settings. PostgreSQL readiness does not use the legacy Entity Objects capacity/permission flags. Leaving those legacy flags in an environment does not authorize a migration or a fallback.

Before testing Coin checkout, confirm that the existing classic PlayFab currency `CO` is defined in this title's **Currency (Legacy)** settings. The website preflight checks the title's currency definitions before accepting a Coin payment. Database verification does not prove this PlayFab configuration. If `CO` is missing, review/create the intended classic Coin definition deliberately; do not overwrite an existing currency or add Diamonds as a legacy currency. No currency definition is created automatically.

## 5. Run the read-only verifier

Install the repository's dependencies and use Node 22.18 or newer. From the website folder:

```powershell
node --env-file=.env scripts/verify-currency-database.mjs
```

This verifier checks the real connected database, installation UUID, title binding, schema version, and runtime role restrictions. It does not install SQL, change privileges, create a wallet, grant Coins or Diamonds, call PayMongo, generate test receipts, or edit `.env`/Vercel settings. It needs no player session ticket.

Only on success does it print the nonsecret verification values. Copy those exact outputs into your private local and Vercel environment settings. If a connection, metadata, schema, role, or binding check fails, no readiness values are emitted and checkout must remain disabled. Mocked test results are not deployment attestations.

The verification fingerprint also binds the physical connection target (protocol, host, port, and database path), not its username/password. Credential rotation for the same target does not change that identity. Choose the runtime endpoint before verification: switching between direct and pooled hostnames changes the target binding even if they reach the same database. Changing the target, installation, title, or schema protocol requires verification again. A cloned database can retain the source installation UUID: that UUID alone is not proof that it is the original current ledger. Do not reuse another target's attestation or assume a provider preview clone is safe for real paid-order fulfillment.

New order snapshots retain their original target identity. Even after verifying a different target, old orders must not silently fulfill against it. A deliberately new installation needs its own UUID; initializing one is not permission to overwrite an old installation identity or existing order snapshots.

## 6. Enable the selected test backend and redeploy

In **your Vercel project's** environment settings, add the restricted `CURRENCY_DATABASE_URL` as a **Secret**, plus the backend selections, installation UUID, and successful verifier outputs. Keep PayMongo on `sk_test_` and preserve your test webhook endpoint. Do not deploy a database-owner/admin connection string. [Vercel environment management](https://vercel.com/docs/environment-variables/managing-environment-variables)

After reviewing all successful verification output, enable the desired test checkout gates:

```dotenv
PLAYFAB_DIAMONDS_ENABLED=true
COIN_CHECKOUT_ENABLED=true
```

The PostgreSQL Coin path uses `COIN_CHECKOUT_ENABLED` and the common verified database gate; do not turn on legacy `PLAYFAB_COINS_RECEIPTS_VERIFIED` as database proof. Redeploy for the new environment values to take effect. Log in with a disposable test account and check that the receiving account is correct. Missing Diamond packages can be added deliberately using the existing administration's **Add Missing Defaults** action; do not overwrite or reactivate disabled packages.

## 7. Verify PayMongo simulation

Complete one simulated purchase at a time, using only [PayMongo's documented test flow](https://docs.paymongo.com/docs/payment-acceptance-testing). Never scan a test QR with a real banking/wallet app; use the documented simulation controls.

- Each Diamond package credits exactly its amount to the authenticated receiving account. Coins and game Gold do not change.
- A Coin purchase changes only classic PlayFab `CO`; PostgreSQL stores its permanent pre-grant claim and confirmation.
- Refreshing a success page or replaying the same signed paid event does not credit again.
- A pending/ambiguous Coin grant remains for operator review. It is not safe to delete its claim or retry a currency increment blindly.
- Log out and test the Diamonds login redirect; expire a session and verify checkout/polling reject it safely. A different player must not read the original player's order.
- Database outages disable checkout/balance availability safely; an unavailable balance is not shown as zero.

Keep live PayMongo keys disabled. The read-only installation verifier proves schema/role/configuration readiness, not every payment scenario; run the repository's mocked currency regressions and the above controlled online checks before broader use.

## Existing wallets and receipts: migration must be reviewed

This installation does **not** automatically copy Entity Object/Economy v2 balances or receipts. It does not reinterpret old pending orders, fall back to a different backend during an outage, or regrant historical paid orders. A reviewed migration must preserve all balances and permanent Diamond/Coin receipts, including pending/uncertain Coin claims and every order's original backend/account/currency/amount. Reconcile ambiguous grants before switching a used title.

Pause purchases, inventory the old ledgers, back up source and destination, define a reviewed import and cutover plan, and validate the imported records before enabling the new backend. Resolve old immutable target-bound orders through their original target or controlled operator reconciliation; do not rewrite their identities to make them payable again. This document is not authorization to import/delete data or alter a player's balance. The current fresh test account can be used only after confirming it has no legacy monetary records; that says nothing about other accounts in the title.

Never restore or switch to a stale database backup/clone while payment fulfillment is running. Classic PlayFab `CO` and PayMongo payments are outside this database: restoring older receipts does not undo their currency grants or payments. Pause checkout/webhooks and reconcile those external services with every permanent receipt and order before any restore/cutover. Target binding rejects a different host/database, but cannot automatically detect a stale restore at the same connection target; an operator must review that recovery explicitly.

Never expire, prune, spend, or automatically delete purchase receipts. Keep database backups and retention appropriate for the ledger, monitor capacity, and make sure administrative access remains separate from runtime credentials. PostgreSQL removes the Entity Objects 8 KiB constraint; it does not remove the provider's own capacity or operational limits.
